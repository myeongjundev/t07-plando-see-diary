# T07 인증 선택 — 판단 재료

상태: **미결. 결정하기 전에 읽는 문서.**
작성 2026-09-03 · 관련 기준 T07-C91~C93 · C101~C115

과제가 요구하는 건 "좋은 인증"이 아니라 **"왜 그것을 골랐는지 한 문장으로 쓸 수 있는
선택"** 이다. 그래서 이 문서는 답을 먼저 적지 않고, 고를 때 실제로 갈리는 축을 적는다.

---

## 0. 먼저 나눠야 하는 것 — 이건 한 개의 결정이 아니다

"인증을 뭘로 붙일까"를 한 덩어리로 놓으면 비교가 안 된다. 실제로는 **서로 독립적인 세 개**다.

| 층 | 정하는 것 | 이게 막는 위협 |
| --- | --- | --- |
| ① 비밀번호 보관 | argon2 / bcrypt / scrypt / PBKDF2 | **데이터베이스가 통째로 샜을 때** 원문 복원 |
| ② 세션 표현 | 서명 쿠키 / 서버 세션 행 / JWT | **탈취된 값의 재사용**, 로그아웃 후 재생 |
| ③ 세션 운반 | HttpOnly 쿠키 / Authorization 헤더 | **XSS로 값 훔치기**, CSRF, 주소창 유출 |

인증 서비스(Auth0 등)를 고르면 세 층을 한꺼번에 남에게 넘기는 것이고, 라이브러리를 쓰면
층별로 다른 것을 고를 수 있다. **아래 1·2·3절을 따로 읽고, 4절에서 조합한다.**

---

## 1. 층 ① — 비밀번호 보관

위협은 하나다: **DB 덤프가 유출된 뒤 오프라인에서 대입**. 그래서 판단 기준도 하나다 —
공격자가 초당 몇 개를 시도할 수 있게 만드느냐.

| 방식 | 성질 | 이 환경(Render Free)에서의 문제 |
| --- | --- | --- |
| **Argon2id** (argon2-cffi) | 메모리 하드. GPU·ASIC 대입이 메모리 대역폭에 막힌다. 2015 PHC 우승, OWASP 1순위 | 기본값이 **메모리 64MiB · 병렬 4**. 인스턴스가 512MB인데 동시 로그인 두 건이면 128MB가 튄다. **매개변수를 낮춰야 한다**(OWASP 최소 권장 m=19MiB, t=2, p=1) |
| **bcrypt** | 20년 넘게 실전에서 깨지지 않음. 메모리는 4KB로 고정 | 메모리 압박 없음. 대신 GPU 대입에 Argon2보다 약하다. **비밀번호 72바이트에서 잘린다**(한글은 UTF-8 3바이트라 24자) |
| **scrypt** (Werkzeug 내장) | 메모리 하드. Flask가 이미 Werkzeug를 깔고 있어 **의존성이 0개 는다** | 기본 n=32768이면 32MiB. Argon2와 같은 고민 |
| **PBKDF2** | FIPS 승인. 가장 오래됨 | 메모리를 안 쓴다 = GPU에 가장 유리. 새로 만드는 것에 고를 이유가 없다 |

**여기서 실제로 갈리는 것**: 이 앱은 Render Free — **CPU 0.1 코어에 512MB**다. 어느 걸
고르든 **매개변수를 측정해서 정해야 한다.** 로그인 한 번에 3초가 걸리면 그건 보안이
아니라 고장이다. 목표는 *로그인 응답 500ms 안쪽*, 그 범위에서 가장 비싸게.

> 이건 문서에 적을 게 아니라 **재 봐야 아는 값**이다. 세 후보를 이 인스턴스에서 돌려
> 시간을 재고, 그 표를 그대로 설명서 ②에 넣으면 "왜 골랐나"가 측정값으로 답해진다.
> — 이게 이 과제에서 가장 점수 되는 문장이 될 것 같다.

C107은 "널리 쓰이는 라이브러리에 맡길 것"을 요구한다. 위 넷 다 라이브러리다. **직접
해시를 조합하는 선택지는 없다.**

## 2. 층 ② — 세션 표현. 여기가 진짜 결정이다

기준 C109·C114가 요구하는 장면은 하나다:

> **로그아웃한 뒤, 같은 주소에 같은 값을 다시 보내면 거절된다.**

이 문장이 선택지를 대부분 잘라 낸다.

| 방식 | 로그아웃이 실제로 하는 일 | C109·C114가 나오나 |
| --- | --- | --- |
| **Flask 서명 쿠키** (기본 `session`, Flask-Login 기본) | 브라우저 쿠키를 지운다. **서버는 아무것도 모른다** | ✗ 지워진 쿠키를 curl로 다시 보내면 **그대로 통과한다**. 장면이 안 나온다 |
| **서버 세션 행** (DB에 세션 한 줄) | 그 줄에 `revoked_at`을 찍는다 | ✓ 같은 쿠키 → 조회 → 폐기됨 → 401. 그대로 증거가 된다 |
| **JWT (무상태)** | 클라이언트가 버린다 | ✗ 서명이 살아 있으므로 만료 전까지 계속 통과 |
| **JWT + 폐기 목록** | 목록에 jti를 넣는다 | ✓ 되지만 — 목록을 DB에 둬야 하므로 **결국 DB를 읽는다**. 무상태의 이점이 사라지고 부품만 는다 |
| **서명 쿠키 + 사용자 에폭** (`session_epoch` 증가) | 그 사용자의 **모든** 세션이 끊긴다 | △ C114(비밀번호 변경)는 되는데, **"이 기기만 로그아웃"이 안 된다.** C109를 만들려면 로그아웃도 전체 로그아웃이어야 한다 |

**생각해 볼 지점 — 왜 업계는 JWT를 그렇게 쓰는가**: JWT의 값어치는 *여러 서비스가 DB를
공유하지 않고 서로의 토큰을 믿을 때* 나온다. 이 앱은 **Flask 하나 + Postgres 하나**다.
믿음을 나눠 가질 상대가 없다. 그러면 JWT는 "DB를 안 읽어도 된다"는 이점만 남는데,
로그아웃을 만드는 순간 그 이점을 스스로 반납한다.

반대로 세션 행의 대가도 적어 둔다: **요청마다 DB 조회 한 번**. Neon Free는 잠들었다
깨는 데 시간이 걸리므로, 이 조회가 콜드스타트에 얹힌다. 인덱스 하나(`token_sha256`
unique)로 끝나는 조회지만 공짜는 아니다.

**Render Free가 끼어드는 지점**: 인스턴스가 15분 뒤 잠들고 깨면서 **재시작한다.**
메모리에 든 것은 다 날아간다. 그래서 세션을 인메모리로 두는 선택지(Flask-Session의
`filesystem`/`memory` 백엔드)는 **로그인이 아무 이유 없이 풀리는 앱**이 된다. 같은
이유로 **무차별 대입 시도 횟수도 메모리에 셀 수 없다** — 세면 재시작 때마다 0이 된다.
막을 거면 그것도 DB다.

### 세션 값을 DB에 어떻게 두나

세션 행을 고른다면 그 안에서 또 하나 갈린다: **토큰 원본을 저장할 것인가.**
비밀번호와 같은 논리로 **SHA-256만 저장**하는 쪽이 맞다 — DB가 새도 그 값으로 로그인이
안 된다. 토큰은 128비트 난수라 사전 공격 대상이 아니므로 argon2까지 갈 필요는 없다.

여기서 딸려 오는 좋은 성질: **서명을 안 하므로 서명 비밀키가 존재하지 않는다.**
C113("비밀키가 브라우저 코드·배포 파일·Git 어디에도 없다")이 *증명할 필요 없이* 참이 된다.
JWT를 고르면 반대로 `JWT_SECRET`이 생기고, 그 키가 어디에도 안 샜음을 따로 보여야 한다.

## 3. 층 ③ — 무엇에 실어 나르나

| 방식 | XSS가 났을 때 | CSRF | 주소창(C112) |
| --- | --- | --- | --- |
| **HttpOnly 쿠키** | 스크립트가 **읽지 못한다**. 다만 스크립트가 대신 요청을 보낼 수는 있다 | **막아야 한다** (SameSite + 헤더 조건) | 안전 |
| **Authorization 헤더 + localStorage** | `localStorage.getItem()` 한 줄로 **털린다.** 털린 토큰은 공격자 서버로 나간다 | 자동으로 안 붙으니 CSRF는 없음 | 안전 |
| 쿼리스트링 | — | — | **즉시 탈락**(C112 위반) |

XSS 대 CSRF의 교환이다. 어느 쪽이 나쁜가: **XSS로 토큰이 빠져나가면 공격자가 자기
기계에서 아무 때나 쓴다. CSRF는 피해자의 브라우저 안에서만, 응답도 못 읽고 동작한다.**
그래서 일반적으로 HttpOnly 쿠키 + CSRF 방어가 권장된다.

이 앱의 유리한 조건: **CSP가 이미 `script-src 'self'`로 잠겨 있다**(T06에서 넣어 둠,
`backend/app/__init__.py`). 인라인 스크립트도 외부 스크립트도 안 돈다. XSS 여지가
애초에 좁다. 그래도 쿠키 쪽이 여전히 낫다고 본다 — CSP는 사람이 실수로 풀 수 있고,
HttpOnly는 안 풀린다.

쿠키를 고르면 **CSRF는 반드시 설계에 들어가야 한다.** 세 가지 층위:
`SameSite=Lax`(브라우저가 막음) / JSON Content-Type 요구(프리플라이트를 강제) /
이중 제출 토큰(직접 구현). 앞의 둘로 갈지, 셋째까지 갈지가 또 하나의 판단이고,
안 하기로 하면 **⑥에 적을 항목**이 된다.

## 4. 현실적인 조합 세 가지

### A. 라이브러리 최소 + 서버 세션 (앞선 설계 초안의 안)

```
① argon2-cffi (Argon2id, 매개변수는 이 인스턴스에서 측정해 결정)
② sessions 테이블 + 불투명 난수 토큰(SHA-256만 저장)
③ HttpOnly·Secure·SameSite=Lax 쿠키 + CSRF 두 겹
```

- 늘어나는 의존성 **1개**. 새 비밀키 **0개**.
- C109·C113·C114가 구조에서 저절로 나온다.
- 대가: 세션 수명·만료·폐기를 **내가 짠 코드가 책임진다.** 틀리면 조용히 안전하지 않다.
- 설명서 ①의 답: "비밀번호는 라이브러리, 세션은 직접 구현" — 갈라서 적어야 한다.

### B. Flask-Login + Flask-Session(SQLAlchemy 백엔드)

```
① argon2-cffi 또는 Werkzeug scrypt
② Flask-Session이 관리하는 서버 세션(DB 저장)
③ Flask 쿠키(HttpOnly/Secure/SameSite 설정) + Flask-WTF CSRF
```

- 세션 수명·쿠키 속성·`login_required`가 **검증된 코드**에 들어간다.
- 늘어나는 의존성 3~4개. 서명 쿠키에 `SECRET_KEY`가 필요 → **C113을 따로 증명해야 함**.
- 로그아웃 시 `session.clear()`가 서버 저장소의 행도 지우는지 **직접 확인해서 적어야
  한다**(백엔드에 따라 다르다). 확인만 하면 C109 장면은 나온다.
- 설명서 ①의 답이 깔끔해진다: "라이브러리, Flask-Login x.y + Flask-Session x.y".

### C. 인증 서비스 (Auth0 / Supabase Auth / Clerk)

- 층 ①②③을 통째로 넘긴다. 무차별 대입·이메일 확인·비밀번호 재설정·2FA가 **딸려 온다** —
  ⑥에 적을 미비점이 크게 준다.
- 그런데 **C103·C104가 막힌다**: "내 데이터베이스에 저장된 비밀번호 해시"를 보일 수
  없고, "같은 비밀번호 두 계정의 해시가 다름"도 보일 수 없다. 남의 서버에 있으니까.
- 카드 2(통과 기준 7개)를 통째로 포기하는 셈이라 **이 과제에서는 성립하지 않는다.**
  다만 "검토했지만 고르지 않은 방법"(C93)으로는 가장 좋은 재료다.

## 5. 수업 맥락에서 한 가지 더

이 과제는 SKT ALEPH의 보안·네트워크 쪽에 걸쳐 있다. 그렇다면 채점 기준을 넘어
**직접 손으로 만져 보는 값**이 있는 조합이 남는 게 많다. A는 다음을 직접 만든다:

- 난수의 출처(`secrets` vs `random`)와 128비트라는 크기의 근거
- 저장 시 해싱 — 왜 세션 토큰은 SHA-256이고 비밀번호는 Argon2인가 (사전 공격 대상 여부)
- 쿠키 속성 네 개가 각각 무엇을 막는가
- 만료를 절대로 둘지 슬라이딩으로 둘지
- 타이밍으로 아이디 존재가 새는 문제(C99를 문구만 맞춰선 안 되는 이유)

B는 이 중 절반을 라이브러리가 대신 정해 준다. **배우려면 A, 안전하려면 B**에 가깝다.
그리고 이 과제는 "안전한가"보다 **"안전한 이유를 댈 수 있는가"** 를 본다.

## 6. 결정 전에 재 볼 것

문서로 더 고민하는 대신 **측정 두 개**를 하면 A/B와 ①의 후보가 대부분 정해진다.

1. **해싱 비용** — Render Free와 같은 조건에서 Argon2id(m=19MiB,t=2,p=1) ·
   bcrypt(cost 10·12) · scrypt(Werkzeug 기본)의 검증 시간을 잰다. 500ms 예산 안에
   무엇이 들어오는가.
2. **세션 조회 비용** — Neon이 깨어 있을 때/잠들었다 깰 때, 인덱스 조회 한 번이 요청에
   얼마를 더하는가.

두 숫자가 나오면 설명서 ②는 "널리 쓰여서"가 아니라 "이 기계에서 이만큼이라서"가 된다.

**어떻게 재는가 (2026-09-03 확인)**: Render Free에는 **대시보드 Shell도 SSH도 없다.**
일회성 잡도 크론도 Free에서는 안 된다 — 그 인스턴스에서 도는 것은 웹 서비스 프로세스
하나뿐이다. 그래서 벤치마크는 **부팅에 얹어 보내고 로그로 받는다**(`BOOT_TASK`).
절차와 되돌리는 법은 `docs/T07-EVIDENCE/00-hash-bench-render-runbook.md`.

노트북 표(`00-hash-bench-local.md`)는 배포 인터프리터와 같은 Python 3.12.13에서 다시
쟀다. 후보 11개 중 3개가 500ms를 넘으므로 이제 표가 조금은 갈리지만, **CPU 기준점이
57.1ms인 기계의 표다.** 0.1 코어에서 이 순서가 그대로 유지된다는 보장은 없다 —
메모리 하드 후보(argon2·scrypt)와 CPU만 쓰는 후보(bcrypt·pbkdf2)는 코어를 좁혔을 때
같은 비율로 느려지지 않는다. 그것이 배포 인스턴스에서 다시 재는 이유다.
