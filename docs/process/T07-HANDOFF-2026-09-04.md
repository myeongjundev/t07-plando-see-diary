## 4. 배포 순서 — 그날 그대로 따라갈 것

`deploy/start.sh`가 `flask db upgrade`를 **BOOT_TASK보다 먼저** 돌린다. 그래서 claim과
NOT NULL은 **같은 배포에 실을 수 없다.** 마이그레이션이 스스로 거부하고 배포를 세운다.

| | 하는 일 | 확인 |
| --- | --- | --- |
| 배포 A | 저장소 연결을 T07로 전환. `BOOT_TASK=claim_t06_data`, `BOOT_TASK_ARGS=--apply` | 로그에 `NULL=0` |
| — | `BOOT_TASK=none`으로 되돌리고 push | |
| 배포 B | `d5a3e91c7f20`까지 올라간다 (NOT NULL 포함) | `/api/live` 200 |
| 그다음 | 관찰 계획을 만들고 그 ID를 `OBSERVATION_PLAN_ID`에 넣는다 | 그 계획의 기록 날짜 0개 |

### Render 환경변수

`render.yaml`에 다 적혀 있다. **대시보드에서 값을 넣어야 하는 것**:

| 키 | 값 |
| --- | --- |
| `DATABASE_URL` | T06 Neon 그대로 |
| `CLAIM_EMAIL` · `CLAIM_PASSWORD` | 이관받을 계정. **명령줄 인자로 주지 말 것** |
| `OBSERVATION_PLAN_ID` | 관찰 계획을 만든 뒤에 |

`JWT_SECRET`과 `IP_HASH_SECRET`은 `generateValue: true`라 Render가 만든다. **둘은 서로
달라야 한다** — 서명 키를 돌린다고 로그인 제한 창까지 초기화되면 안 된다.

claim 대상 ID는 이미 실물 DB로 검증했다: 계획 7개 전부 분류, 삭제될 4개는 살아 있는 할 일
0개, 제외할 할 일 2개는 둘 다 이미 soft-delete 상태.

### 화면 — `/app` 안 계정 화면

세 가지: 비밀번호 변경 폼(현재·새·새 확인), 내보내기, 계정 삭제(**지워진다는 안내 문구

`password_policy_error`로 강제한다).

### 17번은 끝났다 — `POST /api/auth/password`

```
현재 비밀번호 재확인  →  users 행 FOR UPDATE  →  해시 교체 + 전 세션 revoke(password_change)
                                              →  같은 트랜잭션에 PASSWORD_CHANGED 기록
                                              →  commit  →  새 세션 하나 열어 쿠키로 돌려줌
```

- **사용자 행을 먼저 잠근다.** `rotate_session`과 **같은 순서**라 교착이 없고, 「A 검증 →
  변경이 전부 revoke → B insert」로 옛 자격증명에서 새 세션이 살아나는 창이 닫힌다.
- **본인 세션도 죽이고 새로 연다.** 안 그러면 비밀번호를 바꾼 사람이 로그아웃된다. 다른
  기기는 전부 끊긴다 — 그게 C114다.
- 새 비밀번호는 가입과 **같은 함수**(`password_policy_error`)를 지난다.
- 검사 13개 + PostgreSQL 스킵 1개. `test_c114_password_change_revokes_all_sessions`는
  이제 서비스가 아니라 **엔드포인트를 지난다.**
- **주의**: 경합 검사는 SQLite에서 `FOR UPDATE`를 빼도 통과한다(SQLite가 쓰기를 직렬화한다).
  결과는 두 엔진 모두에서 고정되지만, **잠금이 유일한 이유인 것은 PostgreSQL에서만 확인된다.**

### 15번은 끝났다 (`app/services/throttle.py`)

```
창       15분
임계     같은 (email, ip_hash) 실패 5회  또는  같은 ip_hash 실패 20회
```

알아 둘 것 넷:

  나가므로, 상한은 산수로만 도달한다. 그래서 사다리는 `_lock_for`를 직접 검사한다.

## 6-1. 가입 화면 — 정한 것과 안 정한 것

**비밀번호 최소 정책이 생겼다. 서버에도 있다.** 8자 · 영문 · 숫자, **가입 경로에만**.
`parse_credentials(..., enforce_policy=True)`.

- **로그인에는 적용하지 않는다.** 적용하면 이전 정책으로 만든 계정이 잠긴다 — T06 자료를
  이관받은 계정이 그중 하나고, 그 비밀번호는 `parse_credentials`를 지난 적이 없다. 게다가
  Argon2까지 가는 비밀번호보다 빨리 답해서 `dummy_verify`가 지우는 시간차가 되살아난다.
- **대문자·특수문자는 강제하지 않는다.** 강제하면 `Password1!` 모양으로 몰린다. 권장으로만
  둔다. 이 결정과 그 대가는 설명서 ⑥에 적어야 한다 — NIST SP 800-63B는 구성 규칙을
  권하지 않는데 우리는 넣었다.
- **17번에서 비밀번호 변경 엔드포인트를 만들 때 새 비밀번호에도 같은 정책을 적용할 것.**

**가입 버튼이 프런트에서 막힌다**: 이메일 형식 · 최소 정책 · 강도 「보통」 이상 · 확인 일치.
**로그인 버튼은 어느 것에도 묶지 않는다**(위와 같은 이유). 이 제품에는 필수 약관이 없어서
「필수 약관 동의」 조건은 자동으로 만족이다. 동의 체크박스는 넣지 않았다 — 제대로 하려면
동의 시각·버전을 저장해야 하고 그건 아무도 요청하지 않은 스키마 변경이다.

**여전히 넣지 않는 것: 실시간 이메일 중복 확인.** 가입 409가 이미 한 건씩 존재를 드러내고
(C98이 요구, 설계 11절이 한계로 기록), 키 입력마다 답하는 엔드포인트는 그걸 대량 열거로
바꾼다. 로그인이 같은 사실을 감추려고 치르는 비용 — 더미 Argon2 검증, 같은 문구·같은 상태
(C99), 계정 존재와 무관한 429 — 이 전부 무의미해진다. **닉네임**도 그대로 없다.

### 강도 판정 (`frontend/src/auth/passwordStrength.ts`)

순수 함수라 `passwordStrength.test.ts` 26개가 규칙을 고정한다. 손대기 전에 그 파일을 읽을 것.

- **길이가 결정적이다.** `Abc!1234`는 네 종류를 갖춘 8자이고 「강함」이 아니다 — 지시가
  이름을 대어 막은 경우다. 한글도 한 종류로 센다. 안 그러면 한국어 문장 비밀번호가 가장
  나쁘게 표시된다.
- `looksObvious`가 반복·연속 5자·자판 한 줄·흔한 단어를 잡는다. 그래서 `Password1!`은
  규칙을 다 채우고도 「약함」이다.
- **zxcvbn은 검토하고 안 썼다.** 사전을 넣으면 296KB 번들이 배로 뛴다. 온라인 추측에 실제로
  값을 물리는 건 화면이 아니라 서버 잠금(6절)이고 그건 이미 있다.
- **한계**: 유출 목록도 개인 정보도 안 본다. `Myeongjun2026!`은 여기서 「강함」이다. ⑥에 적을 것.
