## 특히 반박해 줬으면 하는 것

번호 순서는 중요도 순이다.

### 1. 하이브리드가 과설계인가

설계 1절이 스스로 인정한다 — **통과 기준만 보면 불투명 세션 쿠키 하나로 충분했다.**
Access JWT + Refresh 회전으로 간 이유는 "회전·재사용 탐지가 붙을 자리"이고, 그건 채점
기준이 아니라 포트폴리오 목적이다. 그 대가로 두 가지를 실제로 치렀다:

- `JWT_SECRET`이 생겼다 → T07-C113("비밀키가 브라우저 코드·배포 파일·Git에 없다")이
  증명해야 할 대상이 됐다. 전에는 서명 키가 존재하지 않아 그냥 참이었다.
- C114 때문에 결국 **요청마다 DB를 읽는다** → 무상태 이점이 사라졌다.

**질문**: 5일 일정 제약까지 놓고 볼 때 이 교환이 남는 장사인가? 부품이 늘어난 만큼
1단계가 늦어지고, 늦어진 만큼 5일 기록이 밀린다. 과설계라고 판단하면 근거를 대라.

### 2. `sid` 바인딩이 정말 C114를 만족하나

```
T07-C114 비밀번호를 바꾸거나 로그아웃하면 이전에 발급한 값이 더는 통하지 않는다.
T07-C109 로그아웃한 뒤 같은 값으로 다시 요청했을 때의 거절 응답이 나란히 적혀 있다.
```

무상태 JWT는 TTL만큼 살아남아 이 기준을 깬다고 판단하고, Access JWT에 `sid`(refresh
session id)를 넣어 가드가 매 요청 그 행을 읽게 했다(설계 1·3절).

**질문**: (a) 이 판단이 맞나 — 무상태 JWT로 C114를 만족시킬 다른 길이 있나?
(b) `sid` 바인딩에 구멍이 있나? (c) 이럴 거면 JWT를 버리고 불투명 세션으로 가는 게
정직한 것 아닌가?

### 3. `last_used_at`을 회전할 때만 갱신하는 것

유휴 만료 48시간의 기준값을 **Refresh 회전 시에만** 쓴다(설계 2·4절). Access TTL이
10분이므로 갱신 주기도 10분이고, 요청당 DB 쓰기가 0이 된다.

**질문**: 유휴 판정이 최대 10분 늦게 반영되는데, 이게 공격자에게 쓸모 있는 창인가?
탭을 열어 두기만 하고 사람은 없는 경우(프런트가 자동 refresh를 돈다) 유휴가 영원히
갱신되어 "유휴 만료"가 무의미해지지 않나? — **이건 내가 놓쳤을 가능성이 높다고 본다.**

### 4. CSRF 세션 바인딩의 셋째 검사

세 겹으로 막는다(설계 5절): `SameSite` + JSON Content-Type 요구 + **세션에 묶인**
이중 제출. 셋째 검사는 `SHA-256(X-CSRF-Token 헤더) == refresh_sessions.csrf_sha256`.

순수 이중 제출은 공격자가 쿠키를 심을 수 있으면 뚫린다고 보고 넣었다.

**질문**: `onrender.com`이 Public Suffix List에 있어 형제 서브도메인이 쿠키를 못 심는
상황에서, 셋째 검사가 실제로 막는 시나리오가 남아 있나? 없다면 부품 하나를 줄여
1단계를 앞당기는 게 맞다.

### 5. 잠금 정책이 C99를 깨지 않나

```
T07-C99 아이디 없음과 비밀번호 틀림이 완전히 같은 문자열·같은 코드로 거절된다.
```

설계 6절: 존재하지 않는 계정의 시도도 세고, 429 문구도 두 경우 같게 뒀다.
5회/15분 → 60초 배증, 최대 15분.

**질문**: (a) 타이밍이나 응답 차이로 계정 존재가 새는 경로가 남았나? 특히 **잠긴 계정과
잠기지 않은 없는 계정**의 응답 시간이 다르지 않나(전자는 Argon2를 안 돌린다)?
(b) 5회·60초·배증·15분 상한의 근거가 설계에 적혀 있는데, 그 수가 방어로서 말이 되나?

### 6. 프런트 자동 refresh의 재시도 루프

401 → `/api/auth/refresh` 한 번 → 원 요청 재시도, 재시도도 401이면 `/login`(설계 8절).
refresh 자체의 401은 재시도 대상에서 뺐다.

**질문**: 동시에 여러 요청이 401을 받으면 refresh가 **동시에 여러 번** 불린다.
회전 설계에서 그건 곧 **재사용 탐지 발동 → 계열 전체 폐기 → 사용자 강제 로그아웃**이다.
양성 오탐이 일상적으로 터지지 않나? 막으려면 무엇이 필요한가?

### 7. 그 밖에 봐 줬으면 하는 것

- 404 vs 403 선택(설계 3절)이 T07-C121과 어긋나지 않나, 그리고 **일관되게** 적용되나
- `security_events.user_id`를 `on delete set null`로 둔 것이 T07-C134(계정과 자료 함께
  삭제)와 충돌하나
- Argon2 매개변수가 아직 ▢인 상태에서, 512MB에 `p=1`·동시 로그인 가정이 현실적인가
- 만료 두 개(48시간·14일)를 테스트에서 시간 주입으로 앞당기는 것(설계 10절)이
  증거로서 받아들여질 만한가
- **설계에 적혀 있는데 증거로 만들 방법이 없는 주장**이 있나 — 있으면 그게 가장 나쁘다
- 1단계 11개 / 2단계 7개 분할(설계 13절)이 5일 제약을 실제로 푸는가, 아니면 1단계가
  여전히 너무 큰가

## 출력 형식

발견을 심각도 순으로. 각 항목에 다음을 붙여라.

```
[심각도] 한 줄 요약
  근거   — 어느 문서 몇 절 / 어느 기준 T07-Cxx
  시나리오 — 구체적으로 무엇이 언제 깨지는가 (추상적 우려는 쓰지 마라)
  제안   — 무엇으로 바꾸나. 바꾸면 1단계 일정이 얼마나 늘어나나
```

심각도는 이렇게 나눈다.

- **깨짐** — 고정 통과 기준을 만족하지 못한다
- **위험** — 기준은 통과하지만 실제로 안전하지 않거나, 운영에서 터진다
- **과설계** — 없어도 기준과 안전이 유지된다. 5일 일정을 생각하면 빼는 게 낫다
- **빠짐** — 설계에 없는데 있어야 한다

마지막에 한 문단으로 답해 달라: **이 설계로 구현을 시작해도 되나, 아니면 무엇을 먼저
고쳐야 하나.**

동의하는 부분은 길게 쓰지 마라. 반박이 필요하다.
