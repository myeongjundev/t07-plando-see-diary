# CI 도입 제안 — 2026-09-11 관찰 종료 이후

**상태: 제안. 지금 적용하지 않는다.**

이 문서는 무엇을 왜 자동화할지만 정한다. `.github/workflows`는 만들지 않았고,
GitHub 설정도 바꾸지 않았다. 구체적인 워크플로 YAML은 적용 시점에 작성한다.

## 적용 시점

**2026-09-11 실제 관찰이 끝나고 운영 응답·내보내기를 Git 밖에 보존한 뒤**에 착수한다.
그 전에는 착수하지 않는다.

이유는 CI의 내용이 아니라 **커밋을 밀어 넣는 행위** 자체에 있다. `render.yaml`에
`autoDeployTrigger`가 없고, Render 문서상 생략 시 기본값은 `commit`이다. 워크플로
파일을 추가하는 커밋을 push하는 것이 곧 운영 재배포가 될 수 있다. 관찰 중에 그
위험을 감수할 이유가 없다.

## 왜 필요한가 — 실제로 놓친 사례

2026-09-08에 새 가상환경에서 백엔드 검사를 돌리자 하나가 실패했다.

```text
FAILED tests/acceptance/test_t07_guide.py::test_c92_guide_versions_match_installed
AssertionError: alembic — assert '1.19.1' == '1.19.2'
```

T07-C92는 `docs/T07-AUTH-GUIDE.md`의 버전 표가 실제 설치된 버전과 일치할 것을
요구한다. Alembic은 Flask-Migrate를 통해 들어오는 전이 의존성이라 직접 버전 제약이
없었고, 새 환경에서는 1.19.2가 잡혔다. 운영 이미지와 가이드는 둘 다 1.19.1이었다.

문제는 드리프트 자체가 아니라 **아무도 몰랐다는 점**이다. 이 검사는 저장소에
존재했고 정확히 동작했지만, 누군가 손으로 pytest를 돌릴 때만 실행됐다. 커밋마다
돌았다면 어긋난 그날 알았을 것이다. 발견이 늦었다면 2026-09-11 최종 배포에서
이미지를 다시 빌드할 때 드러났을 것이고, 그때는 아무도 놀라고 싶지 않은 시점이다.

기준을 코드로 검사해 두는 것만으로는 부족하다. **검사가 자동으로 돌아야 기준이
지켜진다.**

## 무엇을 돌릴 것인가

| 검사 | 목적 |
| --- | --- |
| 백엔드 전체 pytest | 기준 검사를 포함한 회귀 방지 |
| 프런트엔드 테스트 | 화면 로직 회귀 방지 |
| 프런트엔드 프로덕션 빌드 | 배포 산출물이 실제로 만들어지는지 |
| `git diff --check` | 공백·충돌 표지 혼입 방지 |
| 비밀값 감사 (`backend/scripts/audit_secrets.py`) | 커밋된 비밀값 조기 발견 |
| PostgreSQL 전용 검사 (별도 job) | `TEST_DATABASE_URL`이 필요한 3건 |

PostgreSQL 검사를 별도 job으로 분리하는 이유는 서비스 컨테이너가 필요해서다. 기본
job에서는 지금처럼 skip되고, 그 3건이 조용히 사라지지 않도록 전용 job에서 돌린다.

## 설계 원칙

**기준 문장을 CI에 맞추지 않는다.** `docs/T07-ACCEPTANCE-MATRIX.md`의 문구는 고정이다.
CI가 빨갛다는 이유로 기대값을 낮추거나 검사를 지우거나 skip으로 바꾸지 않는다. T06부터
지킨 규칙 그대로이며, CI는 그 규칙을 감시하는 쪽이지 협상하는 쪽이 아니다.

**의존성 버전 드리프트를 계속 감시한다.** C92는 문서와 설치본이 어긋나는 것을 잡는
검사다. 현재 `alembic==1.19.1`로 고정해 두었지만, 앞으로도 전이 의존성이 같은 방식으로
새어 들어올 수 있다. CI가 매번 새 환경에서 설치하므로 이 종류의 드리프트를 가장 먼저
만나는 자리가 된다.

## 한계 — CI가 대신하지 못하는 것

여기를 분명히 해 둔다. CI가 초록색인 것과 과제가 통과하는 것은 다른 얘기다.

- **실제 5일 관찰을 대신하지 못한다.** C04~C08과 C23~C27은 사람이 실제로 일하고
  기록한 결과를 묻는다. 자동화할 수 있는 성질이 아니다.
- **운영 데이터를 검증하지 못한다.** 배포된 인스턴스의 행과 관찰 기록은 로그인된
  브라우저로만 확인된다. `docs/process/T07-DAILY-OBSERVATION-CHECK.md`가 그 절차다.
- **배포본을 검증하지 못한다.** 기준 매트릭스가 "배포본"으로 분류한 항목은 공개 앱에서
  직접 본 것만 근거가 된다.
- **제출문을 검증하지 못한다.** 문서에 적혀 있는지로만 판정되는 항목에는 검사할 코드가
  없다.

## 착수할 때의 주의

- **CI 추가 커밋 자체가 배포를 부를 수 있다.** 최종 배포와 뒤섞이지 않게 순서를 정하고,
  Render의 Auto-Deploy 상태를 먼저 확인한 뒤 push한다.
- 최초 도입은 검사만 붙인다. 브랜치 보호나 자동 병합 같은 정책은 검사가 안정적으로
  녹색이 된 뒤에 논의한다.
- 워크플로가 비밀값을 로그에 흘리지 않는지 확인한다. 비밀값 감사 스크립트의 출력에도
  같은 기준을 적용한다.
