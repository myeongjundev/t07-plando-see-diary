# T07 관찰 기간 일일 확인 — 2026-09-07 ~ 09-11

**이 문서는 관찰이 끝난 뒤의 절차가 아니다.** 관찰 기간 동안 매일, 사람이 로그인된
브라우저에서 직접 수행하는 짧은 확인이다. 2026-09-11 이후의 최종 검증·병합·배포
순서는 `docs/process/T07-FINAL-SUBMISSION-CHECKLIST.md`가 따로 정한다.

## 왜 매일 보는가

5일 관찰은 이 프로젝트에서 가장 빡빡한 제약이고, **되돌리는 방법이 없다.** 기록이
비었거나 순서가 어긋난 것을 2026-09-11에 발견하면 남는 선택지는 타임스탬프를 고치는
것(기준 위반)이거나 5일을 다시 시작하는 것뿐이다. 그래서 매일 확인한다.

확인은 읽기만 한다. 이 문서의 어떤 단계도 데이터를 만들거나 고치지 않는다.

---

## 매일 여는 두 주소

로그인된 브라우저에서 연다. 관찰 계획 ID는 `8848a88f-3814-43dc-a454-f87007b61ba7`로
고정이며, 다른 계획을 보고 있으면 그 시점에 이미 확인이 무효다.

```text
https://t06-plando-see-diary.onrender.com/api/plans/8848a88f-3814-43dc-a454-f87007b61ba7/study
https://t06-plando-see-diary.onrender.com/api/plans/8848a88f-3814-43dc-a454-f87007b61ba7/rule-changes
```

401이나 로그인 화면이 나오면 세션이 끊긴 것이다. 먼저 `/app`에서 로그인한 뒤 다시
연다. **로그인 상태를 확인하지 않은 채 "기록이 없다"고 판단하지 않는다.**

## 1. `/study` — 날짜별 기록

### 먼저 볼 세 값

| 필드 | 있어야 하는 값 |
| --- | --- |
| `planId` | `8848a88f-3814-43dc-a454-f87007b61ba7` |
| `startDate` | `2026-09-07` |
| `endDate` | `2026-09-11` |

이 셋 중 하나라도 다르면 더 볼 것 없이 이상 신호다.

### ⚠️ `days`의 길이로 진행 상황을 판단하지 않는다

**`days`는 관찰 며칠째이든 항상 5개 행을 돌려준다.** 서버가 `startDate`부터
`endDate`까지 모든 날짜를 만들어 채우기 때문이고, 기록이 없는 날은 `executionCount`가
`0`인 행으로 들어온다.

일차 번호를 "기록이 있는 첫날"에서 세지 않는 것은 의도된 설계다. 그렇게 하면 빈 날이
하나 생기는 순간 전체 번호가 밀리고, C09가 말하는 "2일차"와 "3일차"가 읽을 때마다
다른 날을 가리키게 된다.

**진행 상황은 `executionCount > 0`인 행을 세어서 판단한다.**

### 각 행에서 볼 것

| 필드 | 뜻 |
| --- | --- |
| `date` | 서버가 계산한 Asia/Seoul 날짜. 브라우저 시간대와 무관하다 |
| `estimatedMinutes` | 그날 마감인 할 일의 예상 시간 합 (지운 할 일 제외) |
| `actualMinutes` | 그날 **시작한** 실행 기록의 실제 시간 합 |
| `executionCount` | 그날 시작한 실행 기록 수 |
| `ratio` | `실제분 ÷ 예상분` |

### 날짜별 기대값

각 날 종료 시점에 `executionCount > 0`인 서로 다른 Seoul 날짜의 수가 아래와 같아야
한다.

| 확인 시점 | 기록이 있어야 하는 날짜 | 아직 `0`이어야 하는 날짜 | 개수 |
| --- | --- | --- | --- |
| 09-07 종료 | 09-07 | 09-08 ~ 09-11 | 1 |
| 09-08 종료 | 09-07, 09-08 | 09-09 ~ 09-11 | 2 |
| 09-09 종료 | 09-07 ~ 09-09 | 09-10, 09-11 | 3 |
| 09-10 종료 | 09-07 ~ 09-10 | 09-11 | 4 |
| 09-11 종료 | 09-07 ~ 09-11 | — | 5 |

**아직 오지 않은 날짜에 기록이 있으면 안 된다.** 미리 채우는 것은 관찰이 아니다.

### 합계는 직접 더해서 대조한다

화면이나 응답의 합계를 그대로 믿지 않는다. 일별 `estimatedMinutes`와
`actualMinutes`를 손으로 더해서 합계·비율과 맞는지 본다. 계산은
`backend/app/services/metrics.py` 한 곳에서만 하므로 어긋날 이유가 없고, 어긋난다면
그 자체가 조사할 거리다.

## 2. `/rule-changes` — 규칙 변경

### 규칙 변경은 정확히 하나다

2026-09-08(2일차) 실행을 마친 뒤 규칙 변경 **1개**가 기록되어 있어야 한다. 이 변경은
이미 저장되어 있다.

- 2일차 실행보다 **뒤에** 기록되었다
- 3일차 실행보다 **앞에** 있다
- 1일차와 2일차 실행 기록을 각각 하나씩 근거로 인용한다
- 변경 전 규칙과 변경 후 규칙이 구분되어 있다

현재 기록된 변경 후 규칙:

> 작업을 시작하기 전에 10분 단위로 나누고 각 항목을 따로 예상한다.

### ⚠️ 두 번째 규칙 변경을 만들지 않는다

C09가 요구하는 것은 "정확히 한 번"이다. 하나가 이미 있으므로 남은 날에는 규칙 변경을
추가하지 않는다. 3일차 이후에는 **새로 정한 규칙을 따라 일하기만 하면 된다** —
10분 단위로 나누고 항목마다 따로 예상한다.

## 3. 남은 날 매일 하는 일

3일차부터 5일차(09-09 ~ 09-11)까지 매일 같다.

1. `/app`에서 `T07 5일 실제 관찰` 계획을 연다.
2. 새 규칙을 따라 그날 실제로 할 일을 10분 단위로 나누고, **시작하기 전에** 항목마다
   예상 시간을 적는다.
3. 실제로 일한다.
4. 실제 시작·종료와 실제 시간을 기록한다.
5. 위 1·2장의 확인을 수행한다.

### 하지 않는 것

- 비율이 좋아 보이도록 시간을 반올림하거나 조정하지 않는다.
- 날짜를 소급해서 넣지 않는다.
- 그날 하지 않은 일을 기록하지 않는다.
- 예상 시간을 실제를 본 뒤에 고치지 않는다.

이 관찰은 답을 만들어내는 것이 아니라 답이 쌓이게 두는 것이다. 비율이 나쁜 날은 나쁜
대로 근거가 된다.

## 4. 이상 신호와 대응

### 이상 신호

- `planId`, `startDate`, `endDate`가 위 값과 다르다
- 이미 지나간 날짜의 `executionCount`가 `0`이다
- 아직 오지 않은 날짜의 `executionCount`가 1 이상이다
- 실행 시각이 의도한 것과 다른 Seoul 날짜에 들어가 있다
- 규칙 변경이 없거나 2개 이상이다
- 3일차 실행이 규칙 변경보다 먼저 존재한다
- 일별 값을 직접 더한 합계가 화면의 합계와 다르다
- 401 또는 로그인 화면이 나온다

### 대응 순서

1. **로그인 세션과 계획 ID를 먼저 확인한다.** 대부분의 "기록이 없다"는 여기서 끝난다.
2. 화면과 API를 다시 읽는다. 일시적인 표시 문제인지 본다.
3. **기록을 수정·삭제·재생성하지 않는다. 날짜를 소급 입력하지 않는다.** 되돌릴 수
   없는 방향으로 가는 유일한 길이 여기다.
4. 이상이 확인된 시각과 비민감한 사실만 Git 밖의 개인 메모에 적는다.
5. 운영 데이터나 배포 설정을 바꾸지 말고 담당자에게 바로 알린다.

## 5. 저장소에 넣지 않는 것

관찰이 끝나기 전에는 API 응답 원문을 저장소에 저장하지 않는다. 다음은 언제라도
저장소에 들어가면 안 된다.

- 실제 할 일 제목과 내용, 회고 문장
- 이메일, 비밀번호, 쿠키, 액세스 토큰
- 실행 ID, 계정 ID 같은 식별자
- `/study`·`/rule-changes` 응답 본문 전체

대조에 필요한 숫자는 Git 밖의 개인 메모에 적는다. 관찰 종료 후의 증거 보존 절차는
최종 제출 체크리스트 2장이 정한다.

## 6. 배포에 관한 주의

**관찰 기간에는 운영 배포를 하지 않는다.**

`render.yaml`에 `autoDeployTrigger`가 없다. Render 문서상 이 값을 생략하면 신규
서비스의 기본값은 `commit`이며, 그 경우 추적 브랜치로의 push가 재배포를 일으킨다.
대시보드 설정이 blueprint를 덮어쓸 수 있으므로 **`render.yaml`만 보고 현재 상태를
단정할 수 없다.**

- Render 대시보드에서 Auto-Deploy의 현재 값을 사람이 직접 확인한다.
- 켜져 있다면 2026-09-11까지 끌지 여부를 판단한다.
- 확인 전까지는 `origin`에 push하지 않는다.

무료 플랜은 재배포 시 잠시 내려간다. 그 사이가 그날의 기록 시점과 겹치면 하루를
잃을 수 있다.
